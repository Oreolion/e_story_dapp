# Audio privacy fix and production operation

The Nov14 production metadata check found 26 objects in the public `story-audio` bucket, five private stories referencing that bucket and four public stories referencing it. These are aggregate observations: no customer story, object name or media bytes were retrieved, and no disclosure incident is asserted. Public storage is incompatible with the existing story endpoint's author-only voice policy.

The recording form also uploaded an audio blob with `visibility=public` when saving a private entry, despite its text-only notice. The fix uploads only when the user selects public publication. Private saves retain text and send neither an audio-upload request nor an IPFS publication. The component regression exercises recording, unavailable transcription and both actual save handlers with synthetic transports; it does not replace React state or invoke a provider.

`ops/release/storage-audio-privacy.sql` is a **separate proposed production operation**, outside the earlier approved migrations020–023. It has not been applied. It makes only `story-audio` private and adds restrictive INSERT/UPDATE policies for browser roles. Existing permissive policies cannot override those restrictions. Server-managed uploads still use the existing authentication, byte checks and quota; author SELECT and DELETE rules and the avatars bucket retain their behavior. The SQL refuses missing buckets, disabled RLS or incompatible role privileges and commits atomically. Inspect state before retrying after an ambiguous result; policy-name conflicts deliberately refuse a blind rerun.

All objects and story URLs remain stored. The deployed `d0cb70220b3ab1b2c48261578205758d0d1db51e` and candidate story-detail endpoints already check author identity and issue signed audio URLs. The recording preview uses the local blob. Existing public audio URLs, including references previously published elsewhere, will cease to be a supported anonymous playback path after the storage change. This is an intentional privacy restriction; it cannot retract copies already downloaded or guarantee immediate eviction of previously cached content. Do not describe it as zero-impact or silently restore public access as rollback.

The local PostgreSQL-engine test proves the original direct-upload bypass, object/owner preservation, audio-only privacy, browser insert/overwrite/move denial, retained author reads, server uploads, resistance to an additional permissive policy, and whole-transaction rollback on conflict. Required CI runs it alongside the component suite. These tests do not prove the hosted Storage HTTP service, signed-URL delivery or existing CDN state.

Before production execution, bind the reviewed SQL hash and source, recheck the target project `qfwhtsmqndnocfidhdhy`, role/RLS/policy metadata and recovery applicability, and obtain scoped approval for this additional operation. Record a separate production audit decision. Verify metadata/object counts afterward and author playback with a controlled account; never download customer audio as a probe. A synthetic Storage HTTP probe needs its own approved fixture and cleanup plan. Full web cutover still requires current recovery, callback continuity, fencing/drain, schema changes and hosted account acceptance.
