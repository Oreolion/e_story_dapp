# Audio privacy fix and production operation

The Nov14 production metadata check found 26 objects in the public `story-audio` bucket, five private stories referencing that bucket and four public stories referencing it. These are aggregate observations: no customer story, object name or media bytes were retrieved, and no disclosure incident is asserted. Public storage is incompatible with the existing story endpoint's author-only voice policy.

The recording form also uploaded an audio blob with `visibility=public` when saving a private entry, despite its text-only notice. The fix uploads only when the user selects public publication. Private saves retain text and send neither an audio-upload request nor an IPFS publication. The component regression exercises recording, unavailable transcription and both actual save handlers with synthetic transports; it does not replace React state or invoke a provider.

This is a **separate proposed production operation**, outside the earlier approved migrations020–023. It has not been applied. First make only `story-audio` private through the normal Storage API/dashboard. Then `ops/release/storage-audio-privacy.sql` adds restrictive INSERT/UPDATE policies for browser roles. Existing permissive policies cannot override those restrictions. Server-managed uploads still use the existing authentication, byte checks and quota; author SELECT and DELETE rules and the avatars bucket retain their behavior. The SQL refuses a public/missing bucket, disabled RLS or incompatible role privileges and installs both policies atomically. The API setting and policy transaction are separate steps: a policy failure leaves the bucket private. Inspect state before retrying after an ambiguous result; policy-name conflicts deliberately refuse a blind rerun.

All objects and story URLs remain stored. The deployed `d0cb70220b3ab1b2c48261578205758d0d1db51e` story-detail endpoint checks story authorship and issues signed audio URLs, but its substring parser does not establish ownership of the referenced object. The candidate now accepts only canonical URLs from the configured Supabase origin with an exact domain-author folder and a single safe filename. Both save endpoints reject foreign references before database access, and detail reads never sign a mismatched stored reference. The route regression tests cover cross-owner URLs, foreign origins, traversal, encoded separators, credentials, query/fragment ambiguity, anonymous/different viewers, signing failure and legitimate author playback. These tests mock identity validation and database/storage transports; they do not establish hosted account acceptance. A Nov15 aggregate production check found all nine existing audio references compatible with this canonical author-folder format, without retrieving their URLs or content.

The recording preview uses the local blob. Existing public audio URLs, including references previously published elsewhere, will cease to be a supported anonymous playback path after the storage change. This is an intentional privacy restriction; it cannot retract copies already downloaded or guarantee immediate eviction of previously cached content. Do not describe it as zero-impact or silently restore public access as rollback. Until the corrected application artifact is delivered, the older signing parser remains a separate application risk; private bucket configuration alone does not resolve it.

The local PostgreSQL-engine test proves the original direct-upload bypass, refusal of an unprepared public bucket, object/owner preservation, browser insert/overwrite/move denial, retained author reads, server uploads, resistance to an additional permissive policy, and whole-policy-transaction rollback on conflict. Required CI runs it alongside the component suite. These tests do not prove the hosted Storage HTTP service, signed-URL delivery or existing CDN state. [Supabase's Storage schema guidance](https://supabase.com/docs/guides/storage/schema/design) requires record changes through the API; its [bucket API](https://supabase.com/docs/reference/javascript/storage-updatebucket) supports `public:false`.
